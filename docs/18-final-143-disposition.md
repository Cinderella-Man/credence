The file PARSES (Elixir accepts do/else/catch/rescue/after as generic keyword-block options on any call) and fails only during expansion with `error: misplaced operator ->` at the arrow's exact {line, column}. Real and observable. Note the repair is intent-ambiguous, not merely unimplemented: the "obvious" repair (drop the pattern head, keep the body) leaves the pattern-bound variables undefined, and the alternative repair (`after` -> `else`, which compiles and preserves the bindings) silently changes runtime semantics from run-always to run-on-success-only.
- **fix_cond_branch_assignment_in_guard** — Scope-model error in `cond`: an LLM assigns a variable in one `cond` branch body and references it in a LATER branch's guard, expecting sequential/nested scoping (the stab parser is indentation-insensitive, so visually-nested `->` clauses are flattened into siblings). Each `cond` clause is its own scope, so the compiler emits `error: undefined variable "user_key"` at the guard's position plus `warning: variable "user_key" is unused` at the assignment. Observable consequence: the module does not compile.
- **fix_ets_new_string_name** — `:ets.new/2` is called with a binary (usually a string interpolation) as the table-name argument — `:ets.new("#{name}_data", [:set, :named_table])`. ETS requires an atom name. The construct parses, compiles with zero diagnostics, and raises `ArgumentError "1st argument: not an atom"` on every single call. Because table creation is normally done in `init/1`, the observable consequence is a supervisor restart loop / `:max_restarts` shutdown at boot, with no ETS-specific message in the crash reason — the module never runs at all, so the failure has whole-subsystem blast radius. The mechanism is a cross-language habit: names as strings, plus Elixir's `"#{}"` being the reflex interpolation form when `:"#{}"` is required.
- **fix_ets_options_bare_keypos** — The `{:keypos, N}` tuple in an `:ets.new/2` options list gets flattened into two bare list elements — `:ets.new(:t, [:named_table, :set, :public, :keypos, 1])`. The list is a syntactically valid list of atoms plus an integer, so it parses and compiles with zero diagnostics; ETS validates options at runtime and every call raises `ArgumentError: errors were found at the given arguments: * 2nd argument: invalid options`. In a GenServer/Supervisor `init/1` (the usual site for table creation) this surfaces as a start-up/restart loop, not as an ETS error, so the observable consequence is misattributed. Same construct family as the live `no_hallucinated_ets_keytype_option` (bogus option) but a different defect (well-formed option, wrong shape).
- **fix_if_branch_assignment_scope** — Python/JS-transplanted block scoping in `if`: the model assigns the same variable in both branches of a standalone `if` and then reads it after `end`. Elixir branch bindings do not leak, so the read is unbound. Observable consequence, verified: `error: undefined variable "new_service"` at the use site and the module fails to compile (CompileError, "cannot compile module M"). The sibling variant — the variable IS bound before the `if` — is worse: it compiles, the conditional becomes a silent no-op (the post-`if` read sees the pre-`if` value), and the only signal is a `variable "x" is unused (there is a variable with the same name in the context...)` warning.
- **fix_if_inline_else_case_block** — Inline keyword `if cond, do: v, else:` whose `else:` value is written as a multi-line `case ... do ... end` on the following lines. Elixir's parser binds `else: case x` (a `case` node with NO body) as the keyword value and then attaches the trailing `do ... end` as a THIRD argument to `if`, producing `if/3` with the `->` clauses orphaned in arg 3. The file parses cleanly, then fails to compile with `misplaced operator ->`. Observable consequence: a hard compile error, positioned on the first `->` line rather than on the `if`, with no rule anywhere in credence able to repair it — the LLM retry budget is spent instead.
- **fix_mixed_required_optional_map_keys** — Generated Elixir puts a keyword-shorthand entry before an arrow entry inside a map — `%{state: atom(), optional(atom()) => any()}` in a `@type`, or `%{state: :init, optional(k) => v}` in a literal. Elixir requires keyword entries to come last in lists and maps, so this is a hard parse error: `unexpected expression after keyword list. Keyword lists must always come last in lists and maps. ... Syntax error after: ` near `"','"`. Observable consequence: the file never reaches the compiler at all, so nothing downstream (dialyzer, credo, the semantic/pattern phases) ever sees it; the whole module is dark. An information-preserving repair exists and was verified to compile — either arrow-ify the keyword entry (`%{:state => atom(), optional(atom()) => any()}`) or move it last (`%{optional(atom()) => any(), state: atom()}`).
- **fix_nested_module_short_reference** — Definition-order alias invisibility for nested modules. A `defmodule Child` nested inside `defmodule Parent` installs its alias LEXICALLY at the point of the nested `defmodule`; any code above it that writes `Child.fun(...)` expands to top-level `Elixir.Child`, which does not exist. Mechanism: Elixir expands aliases at compile time even inside `def` bodies, so "append helpers at the bottom" (fine for plain functions) silently breaks for nested modules. Observable consequence: the file COMPILES — warning only, build stays green under normal settings — and the process dies in production with `UndefinedFunctionError: function Coordinator.start_link/0 is undefined (module Coordinator is not available)`. Executed and confirmed. The compiler already names the exact repair in a "Did you mean" block.
- **fix_oop_style_method_call_syntax** — OOP method-call transplant onto a struct/map receiver: generated code writes `receiver.predicate?(receiver)` (dot-call WITH parentheses) where `receiver` is a struct/map, not a module. This is syntactically valid Elixir and parses cleanly, so it is not a syntax error at all. At runtime the dot-call-with-parens form is `apply(receiver, :predicate?, [receiver])`, which raises ArgumentError: "you attempted to apply a function named :finalized? on a map/struct ... ensure there are no parentheses after the field name, such as map.finalized?". Observable consequence: the function raises the first time that branch is reached; the build is green. Signal depends entirely on receiver type inference — with an untyped parameter the compiler emits ZERO diagnostics (verified `[]`); when the receiver's type is inferable (e.g. `%Bkt{} = bucket`) Elixir 1.20 emits a warning-severity diagnostic "expected a module (an atom) when invoking finalized?/1 in expression: bucket.finalized?(bucket) where \"bucket\" was given the type: dynamic(%Bkt{})". The mode is real; it is also NOT universal — the identical text `m.valid?(m)` where `m` holds a module atom is correct, working code, which is what makes the rule's blanket rewrite destructive.
- **fix_python_format_in_string_interpolation** — Python f-string zero-pad format specifiers leak into Elixir string interpolation: an LLM emits `"#{cents_part:02}"` (Python `f"{cents:02}"`). This is a hard Elixir parse error — the tokenizer reads `cents_part:` as keyword syntax and reports `keyword argument must be followed by space after: ` at the identifier's exact line/column. The file never compiles; the intended semantics are `String.pad_leading(Integer.to_string(expr), N, "0")`.
- **fix_regex_in_guard** — Generated code puts a regex into a guard or pattern — either an inline `~r//` sigil (`def f(s) when is_binary(s) and s =~ ~r/^http/`) or a module attribute holding a compiled Regex (`@re ~r/^a/; def f(s) when s =~ @re` / `def f(@re)`). Regex literals are escaped structs, and neither escaped structs nor the `~r` sigil are permitted in match/guard context. Mechanism: the compiler raises at expansion time — `ArgumentError "invalid expression in guard, the ~r sigil is not allowed in guards"` for the sigil forms, `"escaped Regex structs are not allowed in match or guards"` for the attribute forms. Observable consequence: the whole module fails to compile; no module is produced. The error is loud and self-announcing (Elixir's message even links to the guards docs), and it is not guard-specific — `def f(@re)` with no guard at all raises the same message.
- **fix_rescue_struct_pattern** — Invalid `rescue` clause head written as a struct/map literal instead of an alias. The bare form `rescue %FunctionClauseError -> body` is a hard PARSE error (`syntax error before: '->'` at the `->`), because `%` must be followed by `{` or `Alias{`. The braced sibling `rescue %ArgumentError{} -> body` parses but the compiler rejects it: `invalid "rescue" clause. The clause should match on an alias, a variable or be in the "var in [alias]" format. Got: %ArgumentError{}`. Observable consequence: the whole file fails to load; every function in the module disappears. Valid heads are `Alias ->`, `var ->`, or `var in [Alias] ->`. (The moduledoc's stated cause — "Python's `except ExceptionType as e` idiom" — is fabricated rationale; Python uses no `%`. The construct itself is nonetheless a genuine, executed parse error.)
- **fix_stray_comma_before_when_guard** — Stray comma between a function head's closing paren and its `when` guard — `def positive?(x), when x > 0, do: true` (also split across lines: `def f(x),\n  when x > 0`). The generator treats `when` as one more comma-separated element of the head, the same "`when` overgeneralized as a comma-separated filter" construct the catalogue pairs with fix_when_guard_in_for_comprehension. Mechanism: the Elixir tokenizer cannot start a guard after a comma, so the parser aborts. Observable consequence: the file never compiles — `{:error, {[line: 1, column: 19], "syntax error before: ", "'when'"}}` — and the current 46-rule live syntax set leaves it unrepaired (analyze=[], fix no-op).
- **fix_undefined_params_in_plug_router** — A generated `Plug.Router` route body reaches for a Phoenix-controller binding that Plug.Router never injects. LLM-written webhook/upload routers write `params["provider"]`. Since Elixir 1.15 an unbound lowercase name is a hard compile error, so the module fails to build with `undefined variable "params"` pointing at the exact column. The mechanical repair is `conn.params[...]`. Observable consequence: the router will not compile at all.
- **fix_undefined_struct_in_pattern** — Definition-order error on a *nested* struct module. Inside `defmodule Parent`, a `%Child{field: var}` literal (here in a `try/catch` clause body) is written above the `defmodule Child do defstruct ... end` that defines it. Elixir expands struct literals at compile time even inside a `def` body, and nested-module aliases are lexical/positional, so the reference resolves to top-level `Elixir.Child` (undefined) and the build hard-fails with `Child.__struct__/1 is undefined, cannot expand struct Child`. Observable consequence: the module does not compile at all. The rule's name is a misnomer — the struct is in the clause BODY, not a pattern.

Observable consequence: `error: undefined variable "q_finish"` and the module fails to compile. Real and currently uncaught by the live pipeline.

Mechanism: Elixir scopes function clause bindings to the clause; the callee's scope is empty apart from its own params. Observable consequence: hard compile error `undefined variable "state"` at the exact use site (verified: severity :error, position {23, 36}); the module does not compile at all, so it is loud, not silent.

Observable consequence: hard compile failure of the whole module (CompileError "cannot compile module M"), not a warning. Real, reproduced by execution on Elixir 1.20.2.
- **fix_underscored_pattern_binding_for_body_use** — Head/body underscore naming drift: a pattern binds `_name` (LLM adds the underscore for "proper style") but the clause body then references `name`. `_name` and `name` are distinct bindings, so the compiler emits the hard error `undefined variable "name"` and the module fails to compile. Distinct from the live UsedUnderscoreVariable case (`_name` bound AND used as `_name`, which is only a warning). Real, reproducible, and currently uncaught end-to-end.
- **fix_when_guard_in_for_comprehension** — `when` written as a comma-separated *filter* in a `for` comprehension — `for {name, price, _qty} <- items, when price > 100 do ... end`. Mechanism: `when` is legal in Elixir in a generator *pattern* (`for {a,b} when b>1 <- l` parses fine) and in def/case/fn clause heads, and the generator/filter list is comma-separated, so the guard keyword gets over-generalised into the filter slot. Observable consequence: hard parse failure `{[line: 1, column: 35], "syntax error before: ", "'when'"}` — the file never reaches the compiler. (The moduledoc's "Python-ism" attribution is FALSE: Python has no `when`; its comprehension filter is `if`.)
- **no_agent_update_tuple_wrapper** — An `Agent.update/2,3` callback returns `{:ok, new_state}` instead of the bare new state (Python/`{:ok, _}`-reflex). `Agent.update` assigns the callback's return value as the state verbatim, so the call still returns `:ok` and the process keeps running with a corrupted state `{:ok, %{...}}`. - **no_bare_function_def_syntax** — A function definition emitted without the `def`/`defp` keyword — `init(opts) do … end` written directly in a module body (Python/Ruby-style). Elixir parses it as a compile-time local *call* of arity N+1 (the do-block is an extra argument), so the module fails to compile with `undefined function init/2 (there is no such import)`. The arity being one higher than intended is the tell. Observable consequence: the module never compiles, and no live rule repairs it. A darker variant exists: inside a DSL module where a `use`d macro of the same name/arity IS imported, the missing-`def` form compiles silently and defines something else entirely.

- **no_bare_return_keyword** — LLMs trained on Python emit a bare, argument-less `return` on its own line as an early exit inside an Elixir block. Elixir has no early-exit construct; the parser reads `return` as a variable reference, so the file compiles to `undefined variable "return"` (error, position on the `return` token) and the module never loads. Distinct from the sibling form `return value`, which produces `undefined function return/1`. Observable consequence: the generated module is uncompilable, and — because there is no early exit in the language at all — no line-level edit can restore the intended control flow; only restructuring the body into `if/else` (condition inverted for `unless`) or `with` preserves intent.

- **no_elif_keyword** — Python-to-Elixir translation emits an `if` / `elif` / `else` chain. `elif` is not an Elixir keyword, so `elif <cond> do ... end` is parsed as a call to an undefined function `elif/2` with a do-block, which consumes the `if`'s block boundary. The parser therefore reports a misleading `missing terminator: end` at the module's `do` (not at the `elif`), and if the terminator is supplied the module fails to compile with `undefined function elif/2`. Real, common, and correctly filed in the syntax phase — the target genuinely fails to parse.
- **no_else_in_for_comprehension** — Python-style `for ... do ... else ... end` transplanted into Elixir. Elixir's `for` accepts `:into`, `:uniq`, `:reduce` but never `:else`; the construct is syntactically valid (it parses as a keyword option to the `for` macro) and dies only at expansion with the error-severity diagnostic `unsupported option :else given to for`, followed by `cannot compile module X (errors have been logged)`. - **no_pipe_into_in_expression** — `|>` assumed to bind tighter than `in`. Observable consequence: hard compile failure. The unambiguous repair is re-associating the AST `{:|>, _, [lhs, {:in, _, [rhs, coll]}]}` into `{:in, _, [{:|>, _, [lhs, rhs]}, coll]}` — i.e. `(expr |> fun()) in collection`. Same mechanism as the sibling `no_pipe_into_arithmetic_operator` (`the :/ operator can only take two arguments`), so one rebuilt rule can cover the whole `Macro.pipe` family.
- **no_plug_upload_size_field** — LLM hallucinates a `:size` field on `%Plug.Upload{}` (the real struct has only `:path`, `:filename`, `:content_type`), usually destructured in a function-head pattern: `def validate(%Plug.Upload{path: path, size: size})`. Mechanism: struct keys resolve at compile time, so Elixir's type checker rejects the key. Observable consequence: hard build failure — `elixirc` exits 1 with `error: unknown key :size for struct <Mod>` / `== Type checking failed with errors ==`. Real and currently uncaught. Correct remediation is `File.stat!(upload.path).size`, which is a semantic rewrite, not a key deletion.
- **no_private_fn_called_from_macro_quote** — A `defp` helper called *unqualified* from inside a `quote` block in a `defmacro`. `quote` does not hygienize function calls — the call is emitted into and resolved in the CALLER's context, not the defining module's. Two verified consequences: (1) every `require M; M.macro(...)` call site fails to compile with `undefined function check_order/2 (expected C1 to define such a function or for it to be imported, but none are available)`; (2) if the caller happens to define a same-named function, the macro SILENTLY calls the caller's implementation (verified: `:CALLERS_OWN_IMPL` returned, zero errors, zero warnings at the caller). In both cases the defining module's only signal is `function check_order/2 is unused` — a warning that actively misdescribes a used-but-unreachable function as dead code. Correct remediation is to qualify the call inside the quote (`__MODULE__.check_order(...)`) and make the helper public; promoting `defp`→`def` alone is NOT sufficient.
- **no_private_named_ets_readable_externally** — A GenServer creates a `:named_table` ETS table with `:private` access in `init/1`, then exposes a public API function (not a `handle_call`/`handle_cast`/`handle_info` callback) that does `:ets.lookup` on it. `:private` in ETS means only the OWNING process may read *or* write — the author read it as `defp`/"not globally writable". The public function runs in the CALLER's process, so every call raises `ArgumentError: errors were found at the given arguments: * 1st argument: the table identifier refers to an ETS table with insufficient access rights`. The code compiles with ZERO compiler diagnostics, so it presents as a runtime crash / supervisor restart loop, never as a build failure. `:protected` is the access level that matches the code as written.
- **no_process_send_after_infinity** — `:infinity` passed as the delay to `Process.send_after/3,4`. Mechanism: `Process.send_after` delegates to `:erlang.send_after/3`, which requires a non-negative integer; `:infinity` is a valid timeout sentinel for `GenServer.call/3`, `Task.await/2`, `receive ... after` and `:timer.sleep/1`, so the model over-generalises "timeout" to one type. Observable consequence: `ArgumentError` "errors were found at the given arguments: * 1st argument: not an integer" at runtime, with ZERO compile diagnostics. In `init/1` or a `handle_info` tick loop this is a supervisor start failure / process crash at boot. The latent form is `Keyword.get(opts, :interval, :infinity)` — every test that supplies an interval passes; only the default configuration path crashes.
- **no_process_send_after_literal_infinity** — `:infinity` used as a "never fire" sentinel for `Process.send_after/3`. `Process.send_after` delegates to `:erlang.send_after/4`, which demands a `non_neg_integer` timeout, so an `:infinity` timeout raises `ArgumentError` ("1st argument: not an integer") at runtime with ZERO compile-time diagnostics. The latent form is the field evidence in the rule's own test: `interval = Keyword.get(opts, :interval, :infinity)` then `Process.send_after(self(), :tick, interval)` — every test that supplies an interval passes; the crash only appears on the default configuration path, and inside `init/1` it becomes a failed supervisor start at boot. The correct construct is not to schedule at all (clause split `defp schedule(:infinity), do: :ok`).
- **no_process_send_after_with_variable_infinity** — A GenServer schedules work with `Process.send_after(self(), :msg, interval)` where `interval` is a configurable option whose default (or an admissible value) is the atom `:infinity` — e.g. `interval = Keyword.get(opts, :interval, :infinity)`. `Process.send_after/3,4` delegates to `:erlang.send_after/4`, which demands a `non_neg_integer`; the atom raises `ArgumentError "1st argument: not an integer"` (the index is the BIF's, so it reads as pointing at the wrong argument). The compiler emits ZERO diagnostics for this. In `init/1` it becomes `{:error, {:badarg, [{:erlang, :send_after, [:infinity, ...]}]}}` and a failed supervisor start at boot. It is latent: every test that supplies an explicit integer interval passes; only the default-configuration path crashes. Author's model error: `:infinity` is a valid timeout for `GenServer.call/3`, `receive..after`, `Task.await/2` and `:timer.sleep/1`, so "timeout" gets generalised into one type admitting the atom sentinel — but `send_after` expresses "never" by not scheduling at all.
- **no_process_whereis_with_pid_arg** — `Process.whereis/1` is `atom() -> pid|port|nil` (a *name-registry* lookup); calling it with a pid — canonically `Process.whereis(self())`, the shape LLMs emit when they mean `Process.alive?/1` or `GenServer.whereis/1` — compiles with zero diagnostics and raises `ArgumentError: errors were found at the given arguments: * 1st argument: not an atom` the first time the line executes. Observable consequence: a liveness/registry guard that was meant to make code defensive instead crashes the calling process (in a GenServer callback, kills the server). Real and independent of this module. Catalogued at FAILURE_MODE_CATALOGUE.md:111.
- **no_raise_in_handle_call** — `raise` used as the error-reporting mechanism inside a GenServer `handle_call/3` clause (OTP callback contract treated as ordinary function semantics). Mechanism: the exception propagates out of `:gen_server.try_handle_call/4`, so the server process terminates and loses all state; the caller does not receive an exception it can `rescue` — it receives an `EXIT`/`:noproc`, and every later call to the named server exits `:noproc`. One client's bad argument becomes a whole-service outage. Observable consequence verified by execution below. Zero compile-time signal.
- **no_raw_send_in_genserver_handle_call** — Reply-protocol violation in `handle_call/3`: the `from` argument is destructured as a bare tuple `{caller_pid, _}` and the deferred reply is delivered with `send(caller_pid, result)` from inside a `spawn`/`spawn_link`/`Task.async`, while the callback returns `{:noreply, state}`. `GenServer.call/3` waits in a *selective* receive keyed on the monitor/alias reference it created, so only `GenServer.reply(from, r)` (i.e. a `{ref, reply}` message) completes it. Mechanism: the raw `send` delivers a message that does not match the selective receive. Observable consequence (executed): the caller burns its full timeout and exits `{:timeout, {GenServer, :call, [...]}}`, AND the stray payload is left sitting in the caller's mailbox where its next `receive`/`handle_info` picks it up as its own — a hang plus cross-talk, with nothing logged at the point of the bug. Independent of this module; the shape is real OTP-looking code (deferred reply is a genuine pattern), which is why it survives review.
- **no_send_self_in_task** — `send(self(), msg)` written inside an `fn` passed to `Task.async/1` or `Task.start_link/1` (same class: `spawn/1`). Inside the spawned closure `self()` is the *task's* pid, not the parent's, so the message is delivered to the task's own mailbox and is garbage-collected with it. The parent GenServer's `handle_info/2` never fires, state stays stale, and there is no crash, no warning and no compiler diagnostic of any kind — a fully silent wrong-behaviour bug that typically surfaces only as a test timeout.
- **no_send_to_from_in_handle_call** — Reply-protocol violation in a GenServer `handle_call/3`: the callback treats the `from` reply tag as a message destination and calls `send(from, msg)` instead of `GenServer.reply(from, msg)`, typically alongside a deferred `{:noreply, state}` return. Since OTP 26 `from` is the 2-tuple `{pid, [:alias | ref]}`, and `:erlang.send/2` accepts a 2-tuple destination only as `{registered_name, node}` (both atoms), so the call raises `ArgumentError: 1st argument: invalid destination`. Observable consequence: the server process dies on the first such call, an unhandled-exception crash report is logged with an exact file:line, and the blocked caller is taken down with `(EXIT) an exception was raised: ArgumentError` (it never receives a reply). The bug is deterministic and on the happy path — the callback is broken 100% of the time it is exercised.
- **no_stream_data_constant_with_range** — Silent test vacuity from a wrong StreamData generator: `StreamData.constant(?a..?z)` written where character/integer generation was intended. `constant/1` is `constant(a) :: t(a) when a: var`, so it wraps the Range literally and every generated value is the same `%Range{}` struct (97..122), not a char. The property test runs, passes, and asserts nothing about the intended domain. Zero compiler diagnostics, zero runtime crash — the only observable consequence is a green test that exercises one degenerate value. Real, and independent of this module.
- **no_underscore_pattern_binding_with_bare_body_use** — Head/body naming drift on an underscore-prefixed pattern binding: generated code binds `_old_name` inside a pattern (case clause, function head, tuple destructure) and then references the bare `old_name` in the clause body. Mechanism: in Elixir the underscore is part of the identifier, so `_old_name` and `old_name` are two distinct variables — the underscored one is bound and silently ignored, the bare one was never bound. Observable consequence: a hard compile ERROR `undefined variable "old_name"`, module fails to compile. (Verified by execution: also emits a companion `variable "value" is unused` warning for the sibling binding, but NEVER any warning about `_old_name` itself.)
- **no_validation_rejects_infinity_for_timeout** — Over-narrow argument validation for a timeout/interval option: a guard `unless is_integer(t) and t > 0, do: raise ArgumentError` rejects `:infinity` in the same module whose runtime path branches on `if interval != :infinity`. Mechanism: the model treats "timeout" as one type admitting the `:infinity` sentinel (true for GenServer.call/receive-after/Task.await) but writes an integer-only validator at the door. Observable consequence (executed): `SharedPoolBucket.start_link(cleanup_interval_ms: :infinity)` raises `ArgumentError ":cleanup_interval_ms must be a positive integer"`, so the two `!= :infinity` guards downstream are unreachable dead code and the one configuration the module was written to support cannot be passed. Zero compile diagnostics. Real, but it is the mirror image of catalogue cluster 4's higher-value member (`:infinity` reaching `Process.send_after/3,4`), and the direction of repair is a policy choice (loosen the validator vs. delete the dead branch) that a tool cannot decide.
