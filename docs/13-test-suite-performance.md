**Status:** investigation + proposals · **Date:** 2026-07-11 · **Problem:** the
full test suite scans ~20k corpus files and takes multiple minutes; the
evolution harness's Gate pays that cost **once per candidate rule**, so corpus
latency is directly rule-generation latency (of a 20–50 min rule build, the
corpus scan is the largest deterministic block). Companion items:
`docs/12` C9 (engine hot-path) and
[`credence-evolution-harness/docs/IMPROVEMENTS.md`](../../credence-evolution-harness/docs/IMPROVEMENTS.md)
H5/H19 (Gate mechanics).

Everything below is grounded in measurements taken on 2026-07-11 (32-scheduler
Linux machine, warm VM, `MIX_ENV=test`), using 240 real corpus files (2.66 MB)
from six pinned packages (jason, decimal, plug, tesla, ecto, phoenix) fetched
into the standard `corpus/` cache.

---

## 1. Measured facts

| Measurement | Result | Per file |
|---|---|---|
| `Sourceror.parse_string`, cold first sweep | 3,380 ms / 240 files | ~14.1 ms |
| Same, warm (from the single-rule run below) | — | **~8 ms** |
| Full `Pattern.analyze` (146 rules) | 12,828 ms / 240 files | **~53 ms** |
| Sum of all `rule.check` calls on pre-parsed ASTs | 14,924 ms (timer overhead included) | ~62 ms |
| **Single-rule** `Pattern.analyze(src, rules: [R])` | 1,908 ms / 240 files | **~8 ms** (parse-bound) |
| Full analyze via `Task.async_stream`, 32 schedulers | 1,015 ms | **12.6× speedup** |
| AST cache: `term_to_binary(ast, [:compressed])` decode | 387 ms / 240 files | ~1.6 ms — **5× faster than parse**; cache ≈ 0.95 byte per source byte |
| `discover_rules` | 161 ms first call, 0.24 ms warm | non-issue |
| Corpus-free suite (`mix test --exclude corpus`) | **13.3 s wall, 104 s CPU** | already ~8× parallel; fine |

Two distribution facts that shape the strategy:

- **No hot rule to optimize.** The slowest single rule
  (`NoUnderscoreFunctionName`, 305 ms/240 files) is only ~3× the 146-rule
  average; the top 15 rules together are ~21% of total check time. The cost is
  *structural* — 146 independent full-AST traversals per file — not one
  pathological matcher.
- **A single-rule scan is parse-bound.** At ~8 ms/file, ~95% of a one-rule
  sweep is parsing. Anything that removes or amortizes parsing (P4) multiplies
  with anything that reduces rules-per-scan (P3).

Extrapolation to the ~20k-file corpus: one full 146-rule sweep ≈ 20,000 × 53 ms
≈ **17.7 CPU-minutes** (sample skews toward meaty packages; the real corpus
average is likely somewhat smaller — recalibrate on the box that runs the real
suite, §6).

## 2. Where the time actually goes (structure, not code)

The corpus suite performs **three independent full-corpus sweeps** plus one
pair-level pass:

| Module | What it sweeps | Parallelism today |
|---|---|---|
| `over_firing_test.exs` | `Pattern.analyze` on every file (per-entry tests generated by a `for` in **one module**) | serial within module |
| `fix_safety_test.exs` | its **own** `Pattern.analyze` per file (`:245`) + applies every accepted fix | serial within module |
| `scope_parity_test.exs` | its **own** per-file rule pass + `apply_rule_fix` on candidates | serial within module |
| `fix_breakage_test.exs` | one fix application per accepted finding | `Task.async_stream` (already parallel) |

ExUnit's concurrency unit is the **module**: `async: true` lets these 4–5
modules overlap each other, but the ~500 per-entry tests inside each module run
strictly serially. On a 32-scheduler machine the suite therefore uses ≈3 cores
where ≈13 effective cores are available (measured 12.6× scaling), and the
wall-clock is ≈ one full sweep (the three sweeps run side by side).

The Gate makes it worse in two small ways: its phase 2 runs the **full**
`mix test`, re-paying the 13 s corpus-free suite it just ran in phase 1; and a
candidate that touches only `lib/syntax/` or `lib/semantic/` pays the whole
corpus scan even though every corpus layer is Pattern-only and *cannot* change.

## 3. Proposals, ranked by (speedup ÷ effort)

### P1. Parallelize within the sweeps — module-per-entry + within-entry chunks

Turn each `for {pkg, version} <- Corpus.entries()` test generator into a
generator of **one ExUnit module per entry** (`defmodule` inside the `for`,
`async: true`, same `:corpus` tag), and use `Task.async_stream` over files
*inside* the big-repo entries (elixir_lang, blockscout & friends — otherwise
the slowest single entry becomes the wall-clock floor). ExUnit's default
`max_cases` (2 × schedulers = 64 here) already accommodates ~500 async modules.

Expected effect alone, from the measured 12.6× scaling: **~8 min → ~45–90 s**
for the full suite, no semantic change, no new infrastructure. This is the
single highest-leverage change.

### P2. One sweep instead of three — share the analysis across layers

`over_firing`, `fix_safety`, and `scope_parity` each independently re-analyze
every file. Compute the per-file analysis **once** per suite run (a
`setup_all`-started cache process, or a plain module-keyed ETS filled by the
first layer to need it, keyed by file path) and let all three layers consume
the shared results — over-firing asserts on the findings, fix-safety and
scope-parity use the same findings to select their fix applications.

Effect: removes two of the three sweeps (~3× less CPU). Combined with P1 the
full suite lands around **30–45 s**, at which point the Gate could simply run
it per candidate without further cleverness.

### P3. Rule-scoped Gate scan — don't re-verify 145 rules that didn't change

`Pattern.analyze` findings are **per-rule independent** — the engine
`flat_map`s each rule's `check` over the same parsed AST with no cross-rule
state (`lib/pattern.ex:19,34-41`), and snapshot lines carry the rule name. So
for a Gate candidate the corpus question decomposes by what the staged diff
touches:

| Diff touches | Sound corpus check | Measured cost (20k files) |
|---|---|---|
| only `lib/pattern/<new_rule>.ex` (+tests) | run **only the new rule** (`rules: [R]`); it must produce **zero** findings (nothing is whitelisted for it); fix-safety/scope-parity trivially empty | ~8 ms/file ⇒ ~2.7 CPU-min ⇒ **~13 s** parallel, **~4 s** with P4 |
| only `lib/pattern/<existing_rule>.ex` (bugfix) | run only that rule; diff only **its** lines against the snapshot (`gone` = narrowing, `new` = over-fire); re-run fix-safety for its accepted findings only | same |
| only `lib/syntax/**` or `lib/semantic/**` | **skip the corpus phase entirely** — every corpus layer is Pattern-only | 0 |
| anything shared (`lib/*.ex`, `rule_helpers`, `dsl_guard`, `pattern.ex`) | full corpus suite (P1+P2 make this ~30–45 s) | ~30–45 s |

Implementation: a `mix credence.corpus --only-rule <Module>` mode (the
snapshot filter and single-rule analyze both already exist as primitives), plus
a Gate-side dispatch on the staged paths (the Gate already parses
`--name-status`). This is the change that turns the corpus from "the 8-minute
tax per candidate" into "seconds for the common case" — new single-rule
candidates are the overwhelming majority of Gate runs.

### P4. An on-disk AST cache the corpus can never invalidate

The corpus is **immutable by construction** — hex versions and git SHAs are
pinned precisely so line numbers stay stable. That makes it the perfect cache
subject: parse each file once ever, store
`:erlang.term_to_binary(ast, [:compressed])` beside the source
(`corpus_cache/<entry>/<file>.ast`, keyed by entry pin), and load with
`binary_to_term` (measured 5× faster than parsing; ~2.5 MB per 2.7 MB source,
so ~200 MB for the whole corpus — fine for a gitignored cache).

Where it pays: P3's scoped scans become check-bound instead of parse-bound
(~13 s → ~4 s), and the P2 shared sweep loses most of its parse component.
Where it doesn't: don't bother caching for the one-off full sweep if P1+P2 are
in — the win there is only ~15%.

### P5. Stop paying the corpus-free suite twice at the Gate (harness-side)

`Gate.check_full_suite` runs `mix test --exclude corpus`, then the **full**
`mix test`. Make phase 2 `mix test --only corpus`: same coverage, minus a
duplicated 13 s, and corpus timing becomes separately visible in the Gate log.
One-line change in `cev/evolve/gate.ex` (noted in the harness doc).

### P6. (Later, optional) per-`(file, rule-version)` findings cache

The fully incremental endgame: cache each rule's findings per corpus file,
keyed by `(entry pin, sha(rule source + shared-helper sources))`. A full suite
then recomputes only rules whose hash changed — CI and maintainer re-pins get
the P3 treatment too, not just the Gate. More machinery (hash discipline over
`rule_helpers`/`dsl_guard` inputs); only worth building if P1–P4 leave the
full sweep as a real bottleneck (unlikely).

### P7. Engine micro-items (already filed as C9)

Parse-once-per-change in the fix pipeline, memoized discovery, batched compile
checks — these speed the **validator/fix path** (the harness's per-row
`Credence.fix`), not the corpus suite; they're tracked in `docs/12` C9.
Measured here and worth recording: `discover_rules` is 0.24 ms warm (not the
problem it looks like), and per-rule check cost is flat, so no single-rule
optimization is worth chasing before the structural items above.

## 4. Expected end state

| Scenario | Today | After P1+P2 | After +P3/P4/P5 |
|---|---|---|---|
| Full suite (local / CI / shared-code Gate case) | ~8 min | **~30–60 s** | same |
| Gate corpus phase — new Pattern rule | ~8 min | ~30–60 s | **~4–13 s** |
| Gate corpus phase — Syntax/Semantic rule | ~8 min | ~30–60 s | **0 s** (skipped) |
| Gate total per candidate (excl. agent time) | ~8.5 min | ~1–1.5 min | **~20–40 s** |

Rule-generation throughput bound by the deterministic pipeline rises by
roughly an order of magnitude; equally important, a cheap corpus makes the
*new* oracles proposed elsewhere (gold over-fire scan H1.2, executable
fix-safety H2, semantic-mutant sweeps C18) affordable per-candidate instead of
nightly.

## 5. Ordering and safety notes

1. P5 and the P3 syntax/semantic skip are one-liners with no semantic risk —
   do them first.
2. P1 next (pure test restructuring; keep the per-entry test names so snapshot
   failure messages stay per-package). Watch the big-repo floor: `elixir_lang`
   at ~4k files × 53 ms ≈ 3.5 min serial *must* get the within-entry
   `Task.async_stream`.
3. P2 and P3 change what is computed — land with a one-time A/B: run old and
   new corpus checks side by side on the same tree and diff the verdicts
   (they must be identical by the per-rule-independence argument; the A/B
   proves the implementation honors it).
4. P3's dispatch must be conservative: any staged path outside
   `lib/{pattern,syntax,semantic}/<the rule>.ex` and its tests ⇒ full scan.
   When in doubt, full scan — the fast path is an optimization, never the
   authority.

## 6. Reproducing the measurements

Fetch a handful of pinned packages into `corpus/` (`mix hex.package fetch
<pkg> <version> --unpack --output corpus/<pkg>`), then time, per file:
`Sourceror.parse_string/1`; `Credence.Pattern.analyze/1`;
`Credence.Pattern.analyze(src, rules: [OneRule])`; the same analyze under
`Task.async_stream(max_concurrency: System.schedulers_online())`; and
`:erlang.term_to_binary(ast, [:compressed])` / `binary_to_term` round-trips.
The 2026-07-11 numbers in §1 came from exactly that script over
jason/decimal/plug/tesla/ecto/phoenix (240 files); re-run it on the machine
that hosts the real corpus before committing to the §4 projections.
